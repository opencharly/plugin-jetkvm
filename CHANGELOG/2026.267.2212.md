# 2026.267.2212 — feat(jetkvm): shared console engine, wake-host, and a no-signal screenshot hint

## Summary

Adds the console-installer driver to the `jetkvm` verb on top of the shared
`sdk/kit` console engine, and three upstream-proper integrations.

### 1. `ocr` + `install`, driven by the shared engine (R3)

New `ocr.go` and `install.go`. The console-wizard MECHANISM is `sdk/kit`'s
transport-agnostic `ConsoleWizard`/`ConsoleStep`/`ConsoleTransport` plus the
shared `OCRBytes`/`ConsolePreview` (opencharly/sdk#276, tagged
`v0.2026266.2315`); this module supplies only the jetkvm-specific transport
(`Capture`, `PressKey`, `PressCombo`, `Type`). The pin moves to
`github.com/opencharly/sdk v0.2026266.2315`. `install` connects ONCE and walks an
ordered recipe, OCR-gating each screen.

### 2. `kind: jetkvm` — the configurable device + recipe entity

`schema/jetkvm.cue` gains `#JetkvmDeviceInput` / `#JetkvmInstaller` /
`#JetkvmInstallStep`, and `plugin.go` advertises the `kind: jetkvm` capability.
`kind.go` resolves the entity over the reverse channel (`OpLoad`): a step may
author inline `steps:`/`answers:` OR reference an entity with `device:`/`recipe:`,
with authored fields winning. Answers merge from three sources — `answers_env`
(host env), `answer_secrets` (credential store), then authored `answers` — via
the shared `kit.MergeAnswers`, on BOTH the entity path AND the step path (one
`kit.MergeAnswers` call, no hand-rolled merge). The decoded types are the
CUE-generated `params.JetkvmDeviceInput`/`params.JetkvmInstaller`.

### 3. The OCR wait-for-screen validator

`schema/jetkvm.cue` adds `artifact_contains_text` to `#JetkvmInput`, so a
`screenshot` step can assert OCR text on the captured PNG (the wait-for-screen
primitive) — the validator already implemented in `sdk.RunArtifactValidators`.
(`artifact_min_cast_events` is deliberately NOT added: it validates an asciinema
`.cast` file and this verb produces only PNGs, so it would be dead surface.)

The field is ENFORCED live, not inert: a screenshot step whose
`artifact_contains_text` names text absent from the screen fails the step with the
validator's own message — captured live:

```
FAIL  [jk-artifact-text]  jetkvm: screenshot: artifact_contains_text:
      "ZZZ-absent-probe" not found in the text OCR read from
      "/tmp/jetkvm-ocr-artifact.png" (read 7 characters; first 200: "omARCH")
```

`artifact_text_wire_test.go` pins the wire contract the SDK reads (the desugared
plugin-input MAP key `artifact_contains_text`, matched against the generated
params struct and the served schema) — the same silent-skip guard
`candy/plugin-wl` carries for its `ocr`, because the SDK lookup is by string key
and nothing type-checks it.

### 4. `wake-host` — upstream's `wakeHost`, not a synthetic key press

A controlled host that is **display-asleep** (DPMS) has no HDMI signal, so
screenshots wait forever. Upstream JetKVM has a dedicated fix — the `wakeHost`
RPC (`jetkvm/kvm` `usb.go:108`), which emits the device's own USB HID wake
report. This adds it as the `wake-host` method (mutating → `allow_control`),
distinct from the existing `wol` (magic packet, for a powered-off host).

### 5. A no-signal screenshot fails with a cause, not a bare timeout

When the capture diagnostics boundary is `BoundaryNoRTP` / `BoundaryRTPStalled`
(the device sent **no media**), the error appends a likely-cause sentence naming
`wake-host` and `wol`. Keyed to the boundary (a pure function of the snapshot),
so it costs no extra probe.

### The host OCR dependency (R9)

`ocr`/`install`/`artifact_contains_text` run tesseract on the HOST (via the SDK's
shared `kit.OCRBytes`/`OCRBytesScaled`), and the host provisioning already covers
it: the charly OS package declares `tesseract` + a language pack as an optional
`suggests:` on every family — `charly/packaging/charly.yml:256-257` (arch),
`:300-301` (rpm), `:343-344` (deb) — the same path plugin-wl's `ocr` documents.
No candy `packaging:` change is needed; a missing engine returns a NAMED error
from `kit.OCRBytes`, never a vacuous no-match.
- **R10 — live verification:** the `ocr`/`install`(entity + inline)/`wake-host` paths ran live (pasted above). The ordered multi-step walk and per-screen anchor gating are proven DETERMINISTICALLY (`TestInstall_MultiStepDistinctAnchors`, `TestInstall_DesyncIsCaught`) because a single static device screen cannot exhibit two distinct anchors — the attached machine is on its installed desktop, not the installer, and the wizard anchors are installer-specific.
