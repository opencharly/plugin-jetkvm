# 2026.261.0945 — fix(jetkvm): move/click without a button, and an env-driven device address

## Summary of changes

Five input/interface fixes to the `jetkvm:` verb, all found by **driving the live device and visually inspecting the screenshots**.

1. **`move`/`mouse` failed without a `button:`** — `methodPointer` resolved a mouse button unconditionally, so a *pure move* (which presses no button) died with `unknown mouse button`. Now `move`/`mouse` are **always** pure position moves; an authored `button:` on them is validated but never sent.
2. **`click` and `drag` failed without a `button:`** — the schema documents `button` as *default left*, but the code passed `""` into the resolver. The default is now resolved before dispatch.
3. **`key` and `key-combo` only accepted a hardcoded 15-combo table.** The retired registry (`alt+tab`, `ctrl+c`, …, 15 entries) rejected `F5`, `Return`, arrows, most letters — yet the schema documents arbitrary keys (`Return`, `Escape`, `F5`, `Control_L`) and chords. Replaced with `internal/kvmclient/keymap.go`, a resolver over the **common** USB HID Keyboard/Keypad usages: letters `a`–`z`, digits `0`–`9`, `F1`–`F12`, the navigation/editing keys (`Enter`, `Escape`, `Tab`, arrows, `Home`, `End`, `PageUp`, `PageDown`, `Insert`, `Delete`, `Backspace`), punctuation, and named modifiers, with Shift inferred for uppercase/shifted symbols. Names **outside** that set still fail with `unknown key` (it is a curated common set, not the whole usage page — the docs say so). Every previously-valid name still resolves to the **same** key: e.g. the old registry mapped `t`→`0x17` and the new table maps `t`→`0x04+('t'-'a')=`0x17`, pinned by `TestResolveKeyComboRegressionOldRegistry`. The retired helpers (`normalizeKeyComboName`, `validKeyComboNames`) and the now-unused `KeyUsage*` constants are deleted, not parked.
4. **The `x`/`y` docs said "desktop-absolute coordinates"** (implying pixels), but the wire takes **absolute HID coordinates `[0,32767]`**. Visual inspection caught this: a "move to (960,540)" landed at screen ≈(56,31), i.e. still top-left. The schema + README now state the HID range and the pixel→HID conversion (screen centre = ≈16384,16384).
5. **The device address is env-configurable (`JETKVM_HOST`) and no hostname is committed** — the beds hardcoded a real tailnet hostname in 17 places; they now author no `host:` and take it from `JETKVM_HOST`, like `JETKVM_AUTH_TOKEN`/`JETKVM_PASSWORD`.

The env-driven `jetkvm-input-probe` bed now drives screenshot → move → click → drag → key → key-combo → type → screenshot (8 plan steps), so every changed input branch runs live. Its `charly.yml` header documents the same run procedure as this body — `JETKVM_HOST=<host> JETKVM_AUTH_TOKEN=<token> charly check run jetkvm-input-probe` — no `charly-jetkvm` prerequisite.

**Semantics note (explicit, not silent):** the behaviour changes are (a) previously-FAILING `button:`-less `move`/`click`/`drag` now pass, (b) `key`/`key-combo` accept far more names (all previously-valid ones unchanged), and (c) the committed hostname removal. A `move` with an authored `button:` was a pure move before and is now — pinned by `TestInvokeMoveWithButtonStaysAPureMove`.

**Breaking change + rollback:** `none` for authored plans — explicit `host:` still wins; a `move` with a `button:` keeps pure-move behaviour; every name the old combo registry accepted still resolves. Revert the merge to roll back.
