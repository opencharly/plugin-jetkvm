# 2026.260.1317 — fix(security): gate the rpc escape hatch — it was a device-safety bypass

## Summary of changes

Fixes a **real device-safety bypass** found by the validator on the `layer-charly-check` skill PR: `rpc` was classified read-only, so `rpc_method: factoryReset` (or any other device JSON-RPC method) was reachable with **no** `allow_control` opt-in and no refusal — a documented way around the entire safety gate on a non-disposable physical appliance that controls a real machine's keyboard, video and power.

- `methods.go`: `rpc` moves OUT of `readOnlyMethods` into the default **mutating** class, so it now requires `allow_control: true`. (Also adds the missing `usb-config` read-only entry, which the README already documented.)
- `methods.go`: adds `rpcForbiddenMethods` — `factoryReset`, `tryUpdate`, `tryUpdateComponents` — which the escape hatch refuses **even with** `allow_control`, matching the never-autonomous rule their typed counterparts obey.
- `catalog.go`: `methodRawRPC` enforces that refusal before forwarding the call.
- `README.md`: `rpc` moves to the mutating list, with the reason and the even-with-control refusal stated, so the doc and the code agree.
- `provider_test.go`: the two tests that encoded the disproven premise (`rpc` read-only) are replaced, and three new tests pin the fixed contract.

**Closes / relates to:** `opencharly/layer-charly-check#13` (the skill PR whose review surfaced this). That PR's skill text must land after this fix, since it documents the corrected contract.

**Breaking change + rollback:** this **changes behaviour** for anyone who authored `jetkvm: rpc` without `allow_control`: it now reports the documented skip instead of executing. That is the fix, not a regression — the previous behaviour was the vulnerability. Recover by adding `allow_control: true` (and, for the three irreversible methods, by not calling them at all). Revert the merge to restore the old behaviour (not recommended).
